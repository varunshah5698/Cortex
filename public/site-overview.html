What is on screen

The build environment is the whole product.

One prompt goes in at the bottom of the room. A planner splits it into work units, every specialist publishes an interface before writing anything, all of them reason out loud and then write their own file at the same time, a reviewer reads the result against the verifier's findings, and the runner installs and serves what came out.

01 One room, seven seats

Each seat is a provider, model and role picked in the workshop. The room shows who is thinking, who is writing, and who is waiting on a review.

02 Reasoning you can read

Every file is written twice: once as deliberation in the Reasoning feed, once as code. The feed in the film is that run's own transcript.

03 The preview is a service

The right panel is not a screenshot. The runner detected a static page, served it on a free loopback port, and the panel frames the running document.

Why it can be trusted on screen

Guarantees that show up as behaviour, not copy.

Budgets are checked first

The token and dollar cap is read before the next request, so a run stops between calls instead of after the damage.

Running code needs a yes

Installs, builds and model-authored servers are an approval in the permissions table. The default is deny.

Generated code has its own origin

Previews are served by a second app with no /api, framed without same-origin, so a generated script cannot read the roster.

A check outranks an opinion

The verifier is deterministic and its findings are handed to the reviewer, which cannot approve past a failing check.
